# 1. Git Commit Convention

### 1.1. 기본 구조

Git 커밋 메시지는 다음과 같은 구조를 가집니다

> 헤더: `[Type] <Subject>`<br>
> 바디: `<Body>`<br>
> 꼬리말: `<Footer>`

* 헤더는 한 줄로 작성하며, 바디와 꼬리말은 빈 줄로 구분
* 헤더는 필수이며, 바디와 꼬리말은 선택 사항
* 타입과 제목 사이에는 한 칸의 공백이 있어야 함

### 1.2. 헤더 (Header)
##### 1.2.1. 커밋 유형 (Type)

1. 코드 변경
```
* [feat]: 새로운 기능 추가
* [fix]: 버그 및 오류 수정
* [refactor]: 리팩토링 (Production Code)
    >>> 버그 수정이나 기능 추가가 아닌, 프로덕션 코드(실제 로직)의 구조를 개선(리팩토링)
* [perf]: 성능 개선
```
2. 스타일 및 문서
```
* [docs]: 문서 수정 
    >>> `README.md` 및 기타 문서 수정
* [style]: 코드 스타일 변경
    >>> 코드의 기능적 변경 없이 스타일만 변경. `<ex>`코드 포매팅, 세미콜론 누락, 공백 수정 등
* [design]: 사용자 UI 디자인 변경
    >>> 사용자 인터페이스(UI) 디자인 변경 및 개선. `<ex>`모델, 색상, 레이아웃 등 시각적 요소 수정
```
3. 빌드 및 테스트
```
* [test]: 테스트 코드 관련
    >>> 새로운 테스트 코드를 추가 및 기존 테스트 코드를 리팩토링
* [build]: 빌드 파일 수정
    >>> 빌드 시스템이나 외부 의존성 관련 파일 수정
* [ci]: CI 설정 파일 수정
    >>> Github Actions, Jenkins 등 CI(Continuous Integration) 관련 설정 파일이나 스크립트를 수정
```

4. 파일 및 기타
```
* [chore]: 자잘한 수정
    >>> 기능이나 로직 변경이 없는 자잘한 수정. `<ex>` `.gitignore` 파일 수정, 빌드 스크립트 업데이트, 변수명 변경 등
* [rename]: 파일 혹은 폴더명 수정
* [move]: 파일 혹은 폴더 이동
* [add]: 파일 추가
* [remove]: 파일 삭제
```

##### 1.2.2. 제목 (Subject)
- 50자 이내로 작성
- 첫 글자는 대문자로 작성
- 마침표 및 특수기호 사용 금지
- 명령문 형태로 작성하며 현재 시제 사용
- 간결명료하게 작성
- 헤더의 `[Type]`과 한 칸 띄우기
```
<예시>
[feat] 플레이어 이동 기능 추가
[fix] 플레이어 점프 시 벽 통과 버그 수정
[docs] README.md에 설치 방법 추가
````
### 1.3. 본문 (Body)
- 72자 이내로 작성
- 왜 변경했는지, 무엇을 변경했는지에 대해 자세히 작성
- 변경 사항이 복잡한 경우 여러 단락으로 나누어 작성
- 헤더에서 충분히 설명되지 않은 경우에만 작성
```
<예시>
- 코드 가독성을 개선하기 위해 변수명 및 함수명을 수정.
- 불필요한 주석 제거 및 코드 정리.
- ㅇㅇ 기능의 성능을 향상시키기 위해 ㅇㅇ 알고리즘을 적용.
```
    
### 1.4. 꼬리말 (Footer)
- 이슈 트래커 ID나 참고 링크 등을 작성
- 생략 가능
```
<예시>
Resolves: #123
See also: #456
```

# 2. Branch Management Convention
### 2.1. 브랜치 유형
```
- main: 배포 가능한 상태의 코드가 존재하는 브랜치
- develop: 다음 배포를 위한 개발이 진행되는 브랜치
- feature/<feature-name>: 새로운 기능 개발을 위한 브랜치
- fix/<fix-name>: 버그 수정을 위한 브랜치
- hotfix/<hotfix-name>: 긴급 버그 수정을 위한 브랜치
```

### 2.2. 브랜치 네이밍 규칙
- 브랜치 이름은 소문자와 하이픈(`-`)을 사용하여 작성
- 기능이나 수정 내용을 명확하게 나타내는 이름 사용
```
<예시>
feature/player-movement
fix/collision-bug
hotfix/critical-security-patch
```

### 2.3. 브랜치 관리
- `feature` 및 `fix` 브랜치는 `develop` 브랜치에서 생성
- `hotfix` 브랜치는 `main` 브랜치에서 생성
- 작업이 완료된 브랜치는 `develop` 또는 `main` 브랜치로 병합(Merge) 전에 반드시 코드 리뷰 및 테스트를 거침

# 3. 기타 규칙
### 3.1. 커밋 빈도
- 작업 단위가 명확할 때마다 자주 커밋하여 변경 사항을 세분화

### 3.2. 커밋 메시지 언어
- 커밋 메시지는 한국어로 작성

### 3.5. 문서화
- 주요 변경 사항에 대한 문서화는 필수이며, 커밋 메시지와 함께 관련 문서도 업데이트
```
<예시>
- 새로운 기능 추가 시 README.md에 사용법 추가
- 버그 수정 시 관련 이슈에 해결 방법 기록
```
   
### 3.6. 커밋 메시지 예시
```
<예시>
[feat] 플레이어 이동 기능 추가
- 플레이어가 키보드 입력에 따라 상하좌우로 이동할 수 있는 기능을 구현.

[fix] 플레이어 점프 시 벽 통과 버그 수정
- 플레이어가 점프할 때 벽을 통과하는 버그를 수정.

[docs] README.md에 설치 방법 추가
- 프로젝트 설치 및 실행 방법에 대한 설명을 README.md에 추가.

[style] 코드 포매팅 및 세미콜론 추가
- 코드의 일관성을 위해 포매팅을 적용하고, 누락된 세미콜론을 추가.

[design] 메인 메뉴 UI 디자인 개선
- 메인 메뉴의 레이아웃과 색상을 개선하여 사용자 경험 향상.

[refactor] 플레이어 이동 로직 리팩토링
- 플레이어 이동 관련 코드를 리팩토링하여 가독성과 유지보수성 향상.

[test] 플레이어 이동 기능 테스트 코드 추가
- 플레이어 이동 기능에 대한 단위 테스트 코드를 작성하여 기능 검증.
```
    
### 3.7. 브랜치 네이밍 예시
```
<예시>
feature/player-movement
fix/collision-bug
hotfix/critical-security-patch
```

### 3.8. 주의 사항
- 에셋 파일 등 추가할 경우 깃 이그노어 설정 확인
